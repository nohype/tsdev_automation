# Root-Cause Analysis -- v0.1.0 Batch Operation Hangs (`batch-insert-dir` / `batch-upsert-dir`)

**Date:** 2026-09-02 - **Status:** Revision 3 -- Section 7.1 diagnostic-build spec (file sink, immediate flush) applied and adversarially approved (2026-09-02) - **Method:** hard evidence only -- code analysis at the shipped tag (v0.1.0 == HEAD 81771b4), controlled experiments on a dev machine with identical TS 9.5 (orlib20 9.50.01.3344), live thread-stack capture (Frida), minidumps, orlib20's own crash log. Confidence labels: **[PROVEN]** (code/experiment evidence), **[INFERRED]** (best-supported explanation), **[OPEN]** (requires user-side data).

---

## 1. Executive summary

**Structural root cause [PROVEN].** v0.1.0 batch operations contain **no timeout and no failure containment anywhere** on the orlib20 warehouse-command chain:

- The CLI main thread waits `INFINITE` on the batch worker thread (`tsdev_cli.cpp:2511`).
- Every orlib20 warehouse command dispatch waits `INFINITE` on an in-proc completion event (`warehouse+0x6A`; KB Section 2/Section 3), serviced by an orlib20 worker thread whose handlers make **synchronous out-of-proc COM calls into WHServer.exe** (spawned on demand via COM activation; lifetime is lazy -- E6 observed one instance serving 12 consecutive client runs and lingering 24.5 min; KB Section 4/Section 10).

If WHServer becomes unresponsive (or the orlib20 worker stalls/quietly dies), the completion event is never set, the batch worker waits forever, the main thread waits forever on the worker: **tsdev_cli.exe stays alive at 0% CPU with constant memory and no further output -- the exact field signature.** Reproduced end-to-end (Section 4, E2h) with live stack proof: **batch worker thread** blocked in `WaitForSingleObject` <- `orlib20+0x1cf5ec` (the dispatcher completion wait) <- our insert/verify chain (the main thread simultaneously blocked in the `:2511` join); a second thread blocked in `NdrClientCall2` (RPC into WHServer).

**Two observable failure flavors of the same root [PROVEN]:**
1. **Server unresponsive (suspended/wedged)** -> **silent hang**, no dialog -- the users' primary reported symptom (E2h).
2. **Server dies abruptly (killed or graceful exit mid-COM-call)** -> orlib20 worker thread throws an unhandled C++ exception (`0xE06D7363`, HRESULT `0x800706BA` RPC_S_SERVER_UNAVAILABLE) -> `TSCrash.dmp` + `TSErrorLog.txt` + **TSCrashReport.exe dialog** (reproduced three times). Field users report such dialogs "sometimes" -- consistent with this flavor occurring independently.

**Why users and not dev machines [INFERRED, trigger partially OPEN].** Dev probe runs were small and short (<=26 s, ~20 items, tiny library). User libraries are real and large -- each `enumerateReverseDependents` call iterates **all items in all 8 categories** and invokes the linker per item (`tests/diag_m4_reverse_enum.cpp:47-48`), so per-run dispatch volume scales with total library size (our 20-function probe alone produced ~49,000 enumeration blocks per run), and every dispatch crossing is a chance for the race. The hang point varies arbitrarily per run (user-confirmed), which fits a timing-dependent stall, not a fixed poisoned record. What exactly wedges WHServer/orlib20 on user machines mid-run remains **[OPEN]** -- a diagnostic build (Section 7.1) is the fastest way to close it.

**Usability requirement [stated explicitly]:** the affected users run this tool against their **production** TradeStation installation. Detection and diagnosis alone do not make the tool usable: **it must not crash the user's TS processes and must not risk corrupting the TS library/warehouse.** The crash flavor terminates `tsdev_cli.exe` mid-batch: items processed before the crash persist silently (partial batch state, observed in the 06:54 incident) and no result is reported (stdout stays empty). The corruption risk of a mid-write termination (MWRKArea.wrk, `.ell`/`.xml`, shared `SHARE_WO` section) is **untested [OPEN]** -- see Section 7.3.

**Rare variant (hang right after the TS-path line) [INFERRED].** User-confirmed to occur after previous hung/killed runs. E6 showed WHServer's lifetime is lazy -- one instance served 12 consecutive client runs and lingered 24.5 min with 12 dead clients. A **wedged leftover WHServer** from a previous hung/killed run is reused by the next run's COM activation -> `LoadLibraryW` support-DLL `DllMain`s / `OrlibInit(NULL,1)` / first silent dispatch blocks before any enumeration output. Two post-crash retry samples did not reproduce it (poisoning is non-deterministic -- a *wedged*, not merely exited, leftover is required).

**Not the cause [PROVEN ruled out]:** named-pipe `serve` broker (batch never uses it), TSDev.exe child processes (CLI never spawns any; orlib20 is loaded in-proc), file-lock waits (all read-only, fail-fast), internal tsdev_cli thread deadlocks (no locks exist; main-thread wait is a bare join), console/stderr pipe backpressure (reproduced hang with stderr going to files), unbounded traversal recursion (would crash with stack overflow, not hang), orlib20 version drift ([INFERRED-strong]: dev-machine orlib20 SHA256 `318DB24A...EC18` matches `signatures/v9.50.01.3344.json`, user-confirmed identical TS version, no version-check warnings in user logs; user-side hash not captured).

## 2. Field facts (bug report + user-verified answers)

- v0.1.0, elevated PowerShell, Windows 11 and TS 9.5 identical to dev machines.
- Batch ops (`batch-insert-dir`, `batch-upsert-dir`) hang indefinitely: TS path line always printed; most often the log flood (many `enumerateReverseDependents` blocks ending `elem[0]`..`elem[9]`) stops after an arbitrary block; memory constant, CPU 0%, hours, no error/warning logs.
- User-verified: hangs occur with TS Desktop **open and closed** (even fresh boot, orchart never started); **no** crash dialog during the hang; TSCrashReport dialogs appear on user machines **sometimes**; the init-line hang occurred **after previous hung/killed runs**; in fresh state the batch **always** hangs after one of the enumeration blocks, **which block varies per run**.

## 3. Code facts (v0.1.0)

- Batch path: `main` -> `cmdBatchDir` -> `runBatchAndEmit` (`tsdev_cli.cpp:2495`): 64 MiB worker thread (`:2503`), main joins with `INFINITE` (`:2511`). Worker constructs one `TsDevLib`, per item `findExistPos -> createEntry -> saveSource -> verifyModule` (`:872-1062`).
- `verifyModule` (`tsdev_lib.cpp:1799`): `_VerifyModule_New` (`:1917`) -> post-verify cmd 0x0D dispatch (`:2005`) -> `traverseReverseDependents` (`:2045`, def `:2644`) -> per dependent **completely unlogged** `callVerify` (`:2699`) -> recursion (`:2736`).
- `enumerateReverseDependents` (`:2235`): `refreshCache` (cmd 0x0F/0x4E dispatches) -> per category `_LoadMasterRecsEX@16` (worker cmds 0x07/0x08/0x09) -> per record Ord28/linker-85 -> elem scan -> Ord70.
- Every dispatch = KB Section 3 protocol: mutex `[wh+0x72]` -> `SetEvent([wh+0x6E])` -> **`WaitForSingleObject([wh+0x6A], INFINITE)`**; worker handlers do out-of-proc COM via `warehouse+0xAE` -> WHServer.exe.
- `elem[0..9]` blocks are **data-dependent** (`elemCount` from `linkedRec+0x29`; silent `continue` on SEH fault at `:2332-2334`), not a fixed bound. After a block's last line lies a **silent region** (Ord70 -> Ord28/linker -> `_LoadMasterRecsEx` -> unlogged `callVerify` -> recursion `refreshCache`) -- every exit crosses the dispatch/COM machinery. The TS-path line (`:1090-1127`) is followed by `SetDllDirectoryW`/`LoadLibraryW` x8/`OrlibInit` (`:1216-1319`) -- the init-hang window.
- Shipped binary compiles the `TSDEV_DEBUG` flood into Release (`CMakeLists.txt:97`; ~2.6-26.7 MB stderr per run observed).
- Worker thread is **STA** (`CoInitializeEx` APARTMENTTHREADED, `com_apartment_guard.cpp:22`) with hidden windows (`tsdev_lib.cpp:3085-3097`) and **no message pump** anywhere in our code -- an emulation gap vs. TSDev.exe (a GUI with a pump).

## 5. Root cause statement

**Structural (certain):** the v0.1.0 batch path converts any stall or death in the `tsdev_cli worker thread -> orlib20 dispatch -> WHServer.exe COM` chain into an **eternal, silent, 0%-CPU wait** (or, for abrupt RPC failure, a worker-thread crash with TSCrashReport dialog). There is no timeout, no liveness check, no diagnostic, and no abort path. This is a robustness defect of the CLI's emulation of TSDev.exe: TSDev.exe is a GUI process with a message pump and owns its WHServer interaction; the CLI replicates the calls but not the containment.

**Proximate trigger on user machines (partially open):** something stalls or terminates the WHServer/orlib20-worker chain during long batch runs. Established: it is **not** orchart (hangs without it), **not** stderr routing, **not** a fixed poisoned record (hang point varies). Leading candidates, in order:
1. **WHServer lifetime/wedge dynamics** [INFERRED] -- E6 proves WHServer can outlive clients and be reused; a wedged instance stalls every dispatch of every later run (init-hang variant confirmed "after kills"). Whether a *fresh* WHServer can wedge itself mid-run under real-library load is unproven.
2. **Dispatch-volume race** [INFERRED] -- user libraries make runs 10-100x longer and dispatch counts proportionally larger; a low-probability stall (e.g., COM/ALPC scheduling, STA-without-pump cross-apartment callback into our non-pumping worker thread) becomes near-certain per run. Fits "always hangs, arbitrary point".
3. **Quiet in-proc worker death** [OPEN] -- a worker-thread failure that never reaches the unhandled-exception filter would leave the completion event unset with no dialog. Not yet observed; would be discriminated by the diagnostic build.
4. **External interference (security/AV software)** [OPEN, speculative] -- machine-specific COM/RPC stalls or process suspensions (e.g., AV scanning/injecting into WHServer.exe) could wedge the chain on user machines but not dev machines; discriminable by the Section 7.1 diagnostic build (watchdog shows the blocked call and WHServer liveness at hang time).

## 6. Installation-difference assessment (user's explicit question)

With identical Windows 11 and identical TS 9.5, orlib20.dll is almost certainly identical across machines ([INFERRED-strong]: dev-machine SHA256 `318DB24A...EC18` matches `signatures/v9.50.01.3344.json`; user-confirmed identical TS version; the CLI's version check warns-but-proceeds on mismatch and no user saw warnings; a user-side DLL hash was not captured) -- **binary-layout constants are almost certainly not the differentiator.** What legitimately differs between installations and matters here:

| Factor | Differs? | Relevance |
|---|---|---|
| **Library contents/size** (item count, dependency-graph shape, encrypted/read-only/foreign items) | **Yes, totally** | Drives run duration and dispatch count -> exposure to the race (candidate 2). Primary suspect for "always on users, never on dev probes". |
| **WHServer leftover state** from previous hung/killed runs | Yes | Init-line hang variant (user-confirmed "after kills"); E6 lifetime laziness. |
| TS Desktop (orchart) running | Yes | **Not required** for the hang (user-confirmed). |
| TS install path / registry (`Installing` vs hardcoded `Versions\9.05.00` fallback, 32-bit view) | Yes | Detection robustness only -- users' detection works; not hang-relevant. |
| Console QuickEdit / stderr routing | Yes | stderr **pipe backpressure** ruled out experimentally (E2h hang reproduced with stderr going to files); console **QuickEdit selection** ruled out as root cause (the E2h blocked stack is the dispatch-wait site, not a console write) -- retained at most as a user-side amplifier of apparent freeze duration. |
| Locale/ACP | Yes | Correctness only (name mismatches), not hangs. |

## 7. Recommended next steps (for following teams; nothing implemented yet)

**Overriding product requirement:** users run this tool against their production TradeStation installation. **Detecting and diagnosing failures is necessary but not sufficient -- the tool must not crash the user's TS processes and must not risk corrupting the TS library/warehouse.** A diagnosed hang or a clean, informative error is acceptable; a crashed process with unknown warehouse state is not. Every recommendation below is subordinate to this requirement.

1. **Diagnostic build for affected users (highest value, unblocks everything):** a special build that writes extensive diagnostic logs **to files -- not the console -- with immediate per-write flushing** (e.g. open with `FILE_FLAG_WRITE_THROUGH`, or flush after every write) so the recorded log **survives process death by crash or hang-kill**. Rationale from our own evidence: the shipped stderr flood dies with the console; in our experiments the evidence was only recoverable because stderr happened to be redirected to files. One log file per run (e.g. `tsdev_diag_<pid>_<timestamp>.log`), containing:
   - **enter/leave records with high-resolution timestamps, thread id, command id, category/progId and result** around every warehouse dispatch call site: cmd 0x0F/0x4E/0x0D, `_LoadMasterRecsEx`, `_CreateEntryEX`, root and per-dependent `_VerifyModule_New` -- including the currently **silent** `traverseReverseDependents`/`callVerify` region and recursion depth -- plus the `OrlibInit`/`LoadLibraryW` init steps (the rare-variant window);
   - **per-item batch progress markers** (item name, phase completions: findExistPos/createEntry/saveSource/verify/link/traverse) -- doubles as the partial-batch record required by Section 7.3d;
   - a **watchdog thread**: if no log progress for N seconds, append all thread stacks (module+offset) and the warehouse protocol state (`[wh+0x04]` cmd, `[wh+0x6A]/[wh+0x6E]/[wh+0x72]` handle state, `[wh+0x76]` tid) to the log, write a minidump, then abort loudly;
   - periodic **WHServer liveness samples** (pid, present/absent/responsive).
   Purpose: any future hang or crash on a user machine must unambiguously identify the blocked/failed call, the last completed operation, and the WHServer/warehouse state -- confirming the root cause and enabling an optimal, targeted fix instead of further hypothesis-driven guessing. Ship as a separate diagnostic build (or strictly env-gated) so production builds stay clean; gating the current stderr flood out of production remains Section 7.6.
   - **Status (2026-09-02): IMPLEMENTED, adversarially approved (2 rounds), field-validated on the real warehouse.** Separate CMake target `tsdev_cli_diag` (`TSDEV_DIAG` define; production `tsdev_cli` behavior-identical -- all diag code compiles out). All elements above present, plus review-driven additions: `run.start` record (every run self-identifying), enter/leave at the additional dispatch crossings (findExistPos, saveSource, closeWarehouse, deleteEntry, enumerateCallers 0x0F/0x3B, NotifyLibChanged, linker-85/Ord70 silent region), `SymRefreshModuleList` so orlib20 frames attribute as `orlib20.dll+0x...` in watchdog stacks, abort via `TerminateProcess` (exit 13; `ExitProcess` was field-proven to provoke orlib20's blocking "WHouse in memory" detach dialog), `TSDEV_DIAG_WATCHDOG_SECS` knob (`<=0` disables; non-finite/>86400 falls back to the 60 s default) and a serve idle-heartbeat so healthy idle `serve` brokers are never false-aborted. Field validation (`tmp\exp\diag_verify\`): healthy batch E2E (exit 0, full log coverage); 3/3 deterministic E2h-style WHServer-suspend watchdog fires -- blocked call named (`dispatch.Linker.enter`), stacks show `orlib20+0x1CF5EC` (the Section 1 dispatcher-wait site), warehouse state captured (cmd in flight, evDone not-signaled, mutex held), full-memory minidump, loud stderr, exit 13, **zero dialogs**; idle `serve` survives >75 s with ~15 s heartbeats. Reviews: `tmp\exp\review1_diag_build.md` (round 1 DISAPPROVE -> fixes) and round 2 APPROVE. Pre-fix incident artifacts: `tmp\exp\whouse_incident\`. Production insert/modify/delete E2E gate passed (zero popups). Remaining for goal (a) closure: ship `tsdev_cli_diag.exe` to affected users and collect their logs; Section 7.3 corruption experiments and Section 7.2+ containment remain open.
2. **Containment (minimum bar, not the goal):** WHServer/orlib20 liveness probing from the CLI (process presence + responsiveness), converting the infinite silent wait into a **loud, diagnosed failure** (distinct exit code + message naming the blocked dispatch). Any timeout must fail loudly with diagnostics -- never silently continue. **Loud failure alone does not meet the overriding requirement -- it must be combined with 3.**
3. **Crash & corruption safety (required for usability):**
   - **Determine corruption risk empirically [OPEN]:** forced-crash-during-save experiments on a scratch library copy (kill/suspend WHServer, and hard-kill `tsdev_cli.exe`, at each batch phase -- after `createEntry`, mid `saveSource`, mid `verifyModule`, during `closeWarehouse`) followed by warehouse-integrity verification (existing persistence-integrity SHA checks + TSDev UI open test) and poisoned-state checks on subsequent runs (the user-confirmed init-line hang after kills suggests persistent residue is possible; our two E4 samples were clean, so it is non-deterministic).
   - **Pre-flight integrity check:** run the existing persistence-integrity verification at batch start and report before operating -- never work on a warehouse left inconsistent by a previous crash without saying so.
   - **Prevent the crash flavor at its source:** the orlib20 worker exception is provoked by COM failure to a dying/unresponsive WHServer. Supervise WHServer health and abort *before* dispatching when it degrades; establish what TSDev.exe itself does in the same situation (parity rule). Prevention at the cause -- never exception-swallowing inside orlib20 (hack per AGENTS.md).
   - **Partial-batch semantics:** on any failure, report exactly which items completed (batch manifest state). Today a mid-batch crash emits nothing and leaves partially-inserted items silently.
4. **Emulation gap:** evaluate pumping messages on the batch worker thread (TSDev.exe-equivalent behavior for its STA + hidden windows) -- the E2h second thread sat in a COM modal loop while our worker cannot pump; this is the most structural fix candidate for cross-apartment stalls.
5. **WHServer lifetime policy:** investigate the lazy lifetime (E6) and whether a pre-run liveness check / clean single-instance policy eliminates the init-line hang after kills.
6. **Observability hygiene:** gate the `TSDEV_DEBUG` flood out of Release (or behind an env var) -- 26 MB/run stderr is diagnostic noise and console-block exposure; log the currently silent per-dependent `callVerify` region.
7. **User-side data (parallel):** tail ~50 stderr lines of a hung run + `tasklist /v` during hang + whether WHServer.exe was present/responsive. The diagnostic build supersedes this.
